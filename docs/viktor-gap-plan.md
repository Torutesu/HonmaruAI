# Viktor から盗むもの、盗まないもの

調査日: 2026-09-24。対象: [viktor.com](https://viktor.com/)（Slack / Teams に住む「AI社員」、65,000チーム、$50/月〜のクレジット課金）。

## Viktor が実際にやっていること

| 機能 | Viktor の中身 | 出典 |
|---|---|---|
| 実行する AI | 「監査のやり方を教える」のではなく「監査して PDF を渡す」。クラウド上の自分のコンピュータでコードを書いて実行 | 公式サイト |
| 定期実行 | 「毎朝 MRR・チャーンを投稿」「毎週月曜に売上ダッシュボード」「毎月ボードパック」 | 公式サイト / 各レビュー |
| 自動化の提案 | 依頼のパターンを観察し「頼まれていない自動化」を提案する。レビューで一番評価が高い | thisandthat.chat, lindy.ai |
| 学習メモリ（skills） | 会話とワークフローを観察して「skills」というノートを自分で書き、次から参照する | 公式サイト |
| 成果物 | 生データでなく「整った PDF・スプレッドシート・Web アプリ」 | 公式サイト |
| 危険な操作の前に確認 | メール送信や本番デプロイの前に確認を取る | 公式サイト |
| 開発者向け | OpenAI 互換 API、MCP サーバー（2026年7月） | thisandthat.chat |
| ワークスペースの消去 | 「Clean Workspace」で学習した文脈ごと全消去 | 公式サイト |
| 3,200 連携 | Composio 型の OAuth 連携 | 公式サイト |

### Viktor の弱点（レビューから）

- **受信トリガーがない。** メールや外部からの依頼で自分から動けない。呼ばれるか、スケジュールか。
- **費用が読めない。** 「$50 のはずが $150〜400」「2日で $200 溶けた」。実行前にコストが見えない。
- **チャネル間で記憶が移らない。** Slack のチャネルを跨ぐと同じ説明をし直す。
- **冗長。** 短く答えてほしいときに長い。
- **全員が同じ Viktor を共有**し、個人の文脈を分けられない（本人たちがロードマップに挙げている）。

## 盗まないもの

- **Slack / Teams / Discord に住むこと。** 既存のチャットの上に AI を載せるのは「Slack 2.0」の延長で、このプロダクトの前提（判断のフィードが仕事の場所）と正反対。Slack は *入力元の一つ*（既存の同期）としてだけ残し、出力先・居場所にはしない。
- **3,200 連携の数。** 数は Composio が持っている。足りないのは連携の数ではなく、連携から何を作るか。
- **汎用コード実行サンドボックス。** 判断のレイヤーを作っている会社が汎用エージェントの実行環境を作る理由はない。むしろ逆で、*他のエージェントが人間に判断を仰ぐ先* になる（下の E）。

## 我々がすでに Viktor より先にいるところ

- **受信トリガー**: Gmail / Slack / Notion / メール転送が 15 分ごとに判断カードになる（Viktor はできない）。
- **確認が設計の中心**: Viktor が後付けした「危険な操作の前の確認」は、ここでは全操作の形そのもの（カードをスワイプ）。
- **個人ごとの文脈**: 「How I work」は人ごと・ワークスペースごと。コネクタも個人認可。
- **1判断あたりのコスト**: Jev による判断層で、ルーティングの大半が言語モデルを使わない。

## 足りないもの → 実装するもの

優先順位は「フィードに何が届くようになるか」で付けた。フィードに届かない機能は、このプロダクトでは存在しないのと同じ。

### A. Routines — AI が定期的に仕事をして、結果をカードで届ける（P0）

Viktor の「毎週月曜にダッシュボードを投稿」。我々の形では、**結果がフィードにレポートカードとして届く**。

- 一文で作る: 「毎週月曜9時に先週の決定と滞留をまとめて」→ ローカルの日英パーサが頻度・曜日・時刻を読み取り、残りを指示として保存。モデル不要。
- 頻度: 毎日 / 平日 / 毎週（曜日）/ 毎月（日）。時刻は所有者のタイムゾーン（IANA）。
- 実行: 既存の 15 分 cron が期限の来た routine を最大 25 件実行。材料はチームの判断（期間内の決定、滞留、指標）、Playbook（C）、キーワード検索した過去の決定。モデルがあれば Markdown のレポートを書き、なければ決定論的なダイジェスト（それでも役に立つ）。
- 届け方: `type: notification`, `format: report` のカード。`report.markdown` を持ち、Web ではドキュメントとして描画、.md ダウンロードと印刷（PDF 保存）。通知ハブ経由で push / メール。
- 「朝のブリーフ」はプリセット: 自分待ちの判断、2日以上止まっているもの、昨日決まったこと。
- **コストを先に見せる**（Viktor の最大の不満への回答）: 1回ごとの実コストを routine に記録し、一覧に「1回あたり約 $0.0004」と出す。
- API: `GET/POST /routines`, `PUT/DELETE /routines/:id`, `POST /routines/:id/run`, `POST /routines/parse`。
- 権限: 所有者のみ編集。届け先はワークスペースのメンバーに限る。

### B. Proposals — AI から自動化を提案する（P0）

Viktor で一番評価されている「頼んでいない自動化の提案」。我々の形では、**提案そのものが判断カード**で、承認スワイプ一回で Routine になる。

- 毎日1回（cron の UTC 0時台）、各ワークスペースで「同じ人が似た依頼を 45 日で 3 回以上出している」を検出（タイトルの語の重なり）。
- 検出したら依頼者に `proposal: { kind: "routine", routine: {...} }` 付きの承認カードを送る。「毎週月曜に◯◯を頼んでいます。自動でやりましょうか？」
- 承認 → Routine 作成（リレーの判断フックで実行）。却下 → 同じ提案は二度と出さない（`proposals` テーブルに署名を保存）。
- 1人 1週間に 1 提案まで。提案が多すぎる AI は通知を切られる。

### C. Playbook — AI が判断から学び、次から使う（P0）

Viktor の「skills」。違いは **見える・直せる・消せる** こと、そして学ぶ材料が雑談ではなく *決定とその理由* であること。

- 学習: 理由付きの判断（却下・修正・メモ付き承認）のあと、モデルが「今後も効く規則」を最大1つ抽出（なければ NONE、既存と重複なら NONE）。判断者の枠で課金、モデルがなければ学ばない。
- 明示: 「覚えておいて」— Playbook 画面から直接書ける。
- 範囲: チーム全体。どこから学んだか（カード）を記録。
- 使う場所: ルーター（誰に・どう書くか）、Ask anything、返信ドラフト、Routines。関連度（語の重なり）と新しさで最大 12 件。
- 消去: 1件ずつ、または管理者が「学んだことを全部忘れる」（Viktor の Clean Workspace）。
- API: `GET/POST /memories`, `PUT/DELETE /memories/:id`, `DELETE /memories?orgId=`。

### D. 成果物としてのレポート（P1、A に含む）

- カードの `report.markdown` を安全な自前 Markdown レンダラで表示（見出し・箇条書き・太字・リンク・表は除外）。HTML は一切通さない。
- 「.md をダウンロード」「印刷 / PDF 保存」。

### E. MCP サーバー — どのエージェントも人間に判断を仰げる（P1）

Viktor は「AI 社員」。我々は **AI 社員たちが判断を仰ぐ先**。Claude Code、Cursor、社内エージェントが `request_decision` を呼ぶと、判断が担当者のフィードにカードとして届き、エージェントは `get_decision` で結果を読む。

- `/mcp` に Streamable HTTP（JSON-RPC 2.0、`application/json` 応答）。
- 認証: 個人アクセストークン `hm_…`（ワークスペース単位、SHA-256 で保存、平文は作成時に一度だけ表示、失効可能）。
- ツール: `request_decision`, `get_decision`, `list_pending`, `search_decisions`, `list_members`。
- カードは `sourceApp: "Agent: <トークン名>"` で、送り主はトークンの持ち主。宛先はリレーと同じ規則でワークスペースのメンバーに限る。
- Tools 画面に「エージェントをつなぐ」: トークン作成・失効と `claude mcp add` のコマンド。

### やらないこと（今回）

- iOS 側の画面（Linux 環境ではビルド・検証できない）。API はすべてクライアント非依存なので、次のパスで追加する。
- 汎用のコード実行、Web アプリ生成。

## 実装順

1. DB: `routines`, `memories`, `proposals`, `api_tokens`（schema.sql、すべて `CREATE TABLE IF NOT EXISTS`）
2. Worker: `schedule.js`（パーサと次回時刻）→ `memory.js` → `routines.js` → `proposals.js` → `mcp.js` → index.js のルート → relay の判断フック → cron
3. ルーター / Ask / Draft に Playbook を注入
4. テスト（各モジュール + API + 権限 + ワークスペース分離）
5. Web: Automations 画面、Playbook 画面、レポート表示、Tools のエージェント接続、⌘K と i18n
6. PROGRESS.md、README
