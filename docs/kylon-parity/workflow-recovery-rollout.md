# Workflow recovery and old-Worker drain: audit and rollout prerequisites

Status: research only, 2026-11-02. Repository baseline inspected: main `3caf3987e2ae7920ca009d2ddab94bb0ac749d6a`. The prototypes described below are local experiments, not released behavior. This document does not claim Kylon parity, production safety, or exactly-once external effects.

## Observed in the baseline

- Workflow execution has several entry paths: HTTP and MCP operations, record-change triggers, scheduled runs, incoming webhooks, and approval decisions. [index.js](../../worker/src/index.js), [routes.js](../../worker/src/harness/routes.js), [mcpTools.js](../../worker/src/harness/mcpTools.js), [workflows.js](../../worker/src/harness/workflows.js), and [relay.js](../../worker/src/relay.js) contain these paths. In particular, an approval handled by `OrgRelay` can continue a workflow; stopping new HTTP starts alone is not a drain.
- The deployment workflow applies D1 schema and column migrations before deploying the Worker and then checks health and encryption. It does not demonstrate that old invocations, Durable Objects, jobs or their effects have completed. See [deploy-worker.yml](../../.github/workflows/deploy-worker.yml). The configured staging D1 identifier is a placeholder in [wrangler.toml](../../worker/wrangler.toml); whether a suitable existing staging database is available has not been verified. Do not create a paid service to fill this gap.
- A run can perform a step's effect before its progress is durably recorded. A missing step receipt is therefore not evidence that a legacy effect did not happen. The current normal workflow path does not provide an atomic receipt for every post, row mutation or external effect. Row-change callbacks run after row changes; retries and follow-on work require their own analysis.
- The current active-run checks count `running` and `waiting`. The partial `idx_hx_runs_active` index covers those states and is not unique. A new hold state would require consistent changes to admission, safety accounting, queries, notifications, cards, scheduling and clients; adding a status alone is insufficient.
- Workflow posts share the general message mechanism, including an AI-kind path without a workflow-specific author. A blanket database gate on such messages could also block ordinary Simple chat, and a workflow row-only gate would not stop posts, follow-ups, external calls or existing jobs. No complete, narrowly scoped old-code barrier has been established.
- The runner and gateway can execute workflow programs on a configured Mac node. A job's control-plane status, timeout or health response alone does not establish whether an already-issued external effect happened or whether every old process and request has stopped.

## Platform facts and their limits

Cloudflare documents that a Durable Object's default deferred code update can continue serving new requests with old code for up to 300 seconds after a Worker deployment; hibernation or expiry of that delay triggers an update. The `immediate` strategy resets objects, potentially interrupting work and WebSockets, and applies to exported classes. The strategy is write-only, so a configuration read alone does not establish which strategy was used. See [Durable Object code updates](https://developers.cloudflare.com/durable-objects/deployments/durable-objects-code-updates/).

Version skew is possible during [gradual deployments](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/). Even a deployment at 100% or an elapsed timer does not by itself prove that all old invocations, Durable Objects, queued work, gateway effects and externally issued requests have drained. The Worker runtime-update grace period in [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) must not be treated as a general code-deployment or application-drain guarantee. A [Worker rollback](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/) does not roll back D1 state. Version metadata could help observe newly instrumented requests, but cannot prove that an uninstrumented old invocation is absent.

## Local evidence, not deployed functionality

- In synthetic local D1 tests, an approval followed by a post and a later legacy step failure could result in a repeated post when restarted. A hold prototype preserved the prior input, approval and progress, but a simulated old writer could still commit after the new run entered hold. Its busy webhook and cron cases also showed that simply holding a run can lose or skip an incoming event or scheduled slot. These are local observations of the prototype, not claims that the proposed hold state exists in production.
- A separate synthetic D1 batch fixture atomically committed a row mutation, step receipt and progress, rejected a delayed old lease after generation change, and exercised rollback, duplicate claims and a lost response. This is not wired into the production runner. A legacy missing receipt remains ambiguous; posts, notifications, provider calls and other external effects are outside that transaction.
- An unreleased outbox experiment uses event identity, claims and dispatch state to avoid blindly repeating uncertain dispatch. It is not part of the baseline. Integrating a step receipt with it would need one proven transaction and stable event identity; event provenance, old code and uncertain delivery still need explicit handling.
- Recovery UI and API sketches are local fixtures only. They do not provide a production recovery endpoint or server-side execution gate. Existing visibility checks cannot be assumed to authorize disclosure of all inputs, outputs, sources or even workflow existence after access changes.

The synthetic row/receipt batch used seven SQL statements and locally reported eight rows read and five rows written, excluding claim, authorization, validation and outbox work. Another maximal-schema fixture observed additional reads for its proposed guard. These measurements are useful for relative investigation only; real D1 behavior, production workload and cost are unverified.

## Required before a rollout can be considered

1. Inventory and gate every execution and continuation path, including old `OrgRelay` approval handling, scheduled and webhook admission, row changes, MCP, gateway jobs and the outbox. Preserve existing Simple chat and existing workflows. An ambiguous prior external effect must not be automatically resent merely because a new receipt is absent.
2. Define durable run admission, source identity and membership generation; record step identity, claim generation, result and progress together where D1 can make the relevant effect atomic. Preserve old runs' input, approvals and completed or unknown steps. Account for identical-value or timestamp ABA and for effects that cannot participate in the D1 transaction. A proposed `reauthorization_required` status is not a production contract until all readers and admission paths support it.
3. Define a recovery API and UI that recheck current session, workspace, workflow, source and relevant record access without leaking unauthorized existence or content. Distinguish recorded completion from externally verified outcome, and require deliberate reconciliation of unknown effects. Validate concurrent reviewers, revoked rights, changed sources and retries. A visual hold indicator cannot substitute for a server-side fence.
4. Test old and new code against a shared synthetic database with controlled pauses at admission, side-effect commit, receipt, response and dispatch. Include old approval handlers, concurrent cron and webhook inputs, repeated event IDs, record triggers, gateway jobs, authorization changes, unknown effects, rollback and legacy clients. Verify no silently dropped input, duplicate side effects or Simple-mode regression.
5. Establish a verifiable drain and rollback procedure covering old HTTP and Durable Object code, active leases, queued dispatch and gateway work. Health, traffic percentage, version telemetry or waiting a fixed interval alone is not such proof. If an old writer cannot be fenced or demonstrably drained, keep the recovery feature disabled and unpublished.
6. After the local evidence and operational design are independently reviewed, determine whether an existing no-new-charge staging environment can safely test real D1 and Durable Object rolling behavior, migration, rollback and usage. Do not use production records or paid external providers for these tests. Measure actual reads, writes and retention against the existing account limits before deciding whether rollout is appropriate.

The existing standalone workflow snapshot semantics, manual execution and session-independent scheduled/webhook execution must be maintained unless a separately reviewed contract changes them. A failed or held legacy run must not be silently restarted, erased or represented as completed merely to make migration easier.
