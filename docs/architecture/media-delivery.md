# 添付ファイル・画像・動画の配信設計

作成日: 2026-10-02 / 調査対象: main `5ba06e3`
前提: [`discord-model-platform-plan.md`](discord-model-platform-plan.md)（以下「基盤計画」）
状態: 提案。段階0はすぐに実装できる修正、段階1以降は導入条件付き。料金は2026-09時点の公開単価を使った試算で、請求実績ではない。

PR #191 の初版をもとに、レビューで指摘した3点を反映して書き直した。

1. 置き場所を基盤計画にそろえる。
2. 短期URLでもキャッシュが効くようにする。
3. 匿名公開の穴を最初に塞ぐ。

あわせて、規模が大きくなったときの原価とセキュリティを数値で決めた。

## 0. 決定事項

| # | 決定 | 理由 |
|---|---|---|
| D1 | **添付のメタデータはワークスペースのデータ**として扱う。基盤計画どおり最終的に WorkspaceDO に置き、移行中は `WorkspaceStore` 経由で D1 を主、DO をミラーとする。D1 に残すのはログイン前に必要なもの（プランの上限値）だけ | 参照の認可・容量カウンタ・削除キューが、メッセージやメンバーと同じストアの1回の読み書きで完結する。テナント分離が構造で保証される。D1 の単一 writer で全テナントが競合しない |
| D2 | **原本と派生物は非公開 R2**（`org/<orgId>/media/<assetId>/<variant>`）に置く。配信は**別ドメインの配信専用 Worker**から、**時間窓で固定した署名URL**で行う | アップロードされたファイルが API と同じ origin で動くのを構造的に防ぐ。配信 Worker は DB を一切読まない |
| D3 | **署名URLは10分単位の窓で固定し、有効期限は10〜20分**。クライアントはURLではなく `asset/variant@version` をキーにキャッシュする | 同じ窓の間はURLが変わらない。端末キャッシュは窓をまたいでも再利用できる。新しい取得の失効は最大20分で、基盤計画のアクセストークン（15分）と同水準 |
| D4 | **段階0（セキュリティ修正）を新モデルより先に出す**。旧カード動画の匿名・1年キャッシュ、全量バッファ、削除失敗の握りつぶしの3つ | どれも小さな変更で、新モデルと競合しない |
| D5 | 画像の派生物は**要求されたときに生成**し、R2 に保存する。初期は Images binding。**変換費が月$100を超えたら JPEG/PNG/WebP を Worker 内の WASM へ移す**（§8） | 10万 MAU では変換費が保存費の2.5倍になる。HEIC など WASM で扱いにくい形式だけ Images に残す |
| D6 | 動画は**H.264/AAC の MP4 を R2 から Range で直接再生**する。iPhone の HEVC はアプリ側で H.264 に書き出す。Stream は非互換動画で組織が有効化した場合だけ使う（段階4） | R2 の直接再生は Stream の約1/100の費用。互換性はアップロード側で作る |
| D7 | 写真は**アップロード時に端末で長辺2560pxへ縮小**するのを既定にする。「原寸で送る」を選べる | 長期の最大費目は保存量（§8）。写真の保存量がおよそ1/3〜1/4になる |

採用しないもの:
- 全動画の Stream 化。
- 全サイズの先行生成。
- 25 MiB 以下での分割転送。
- 配信時のエッジキャッシュ（§5.5）。
- 端末で作ったサムネイルを他人向けの表示に使うこと（原本とすり替えられるため）。

## 1. 現状（main `5ba06e3` で確認）

| 経路 | 現状 | 問題 |
|---|---|---|
| カード動画 `worker/src/media.js` | 12 MiB 上限。キーは UUID だけで org なし。`GET /media/:uuid` は**無認証**で `Cache-Control: public, max-age=31536000, immutable`。Range 非対応 | URL を知っていれば誰でも取得できる。共有キャッシュに1年残る。テナントの所有が不明 |
| チャット添付 `worker/src/files.js` | 25 MiB・10件。`org/<orgId>/files/<id>`。署名URLは日の境目で丸めた24〜48時間有効。配信のたびに D1 の `message_files` を読む（Range ごとにも） | 退出・削除後も最大48時間取得できる。動画再生で D1 の読み取りが増える。署名鍵が D1 の `kv` にある |
| 配信 origin | 添付は API と同じ origin で、CSP の sandbox と `nosniff` で防いでいる | 防御は1層だけ。API の origin でアップロード物が実行される余地を構造的に消したい |
| アップロード | `readCapped` がチャンクを保持したうえで結合バッファを確保する（ピークは約2倍）。種類は申告された Content-Type をそのまま信用 | 25 MiB×同時数で isolate のメモリ128 MB を圧迫する。種類の偽装を検出しない |
| 削除 | `deleteFileObject` が `.catch(() => {})` で失敗を握りつぶし、その後メタデータを消す | 消したはずのバイトが R2 に孤立して残る（漏洩と保存費） |
| 画像 | 一覧でも原本を取得 | 回線と描画の負担。HEIC はブラウザで表示できない |
| その他の blob | 絵文字・アイコン・アバター・Jam 録音は org 接頭辞なしのキー | この設計の対象外。基盤計画 §4.6 のワークスペース移行で扱う |

`media.js` の「R2 は保存だけが課金対象」というコメントは誤り。Class A/B の操作も課金される。

## 2. データモデル（ワークスペースのデータ）

`WorkspaceStore` のインターフェースで定義する。

- 移行中は D1 の実装が主で、`WORKSPACE_DUAL` のワークスペースは DO にミラーする。
- 切り替え後（基盤計画 M4）は DO が主になる。
- テーブルはどちらのストアでも同じ形にし、`reconcile` の対象に含める。

| テーブル | 列 | 制約・索引 |
|---|---|---|
| `media_assets` | `id`（UUIDv7）, `kind`（image/video/audio/file）, `type`（検証後の MIME）, `name`, `size`, `width`, `height`, `duration_ms`, `codec`, `uploader`, `version`, `state`, `created_at`, `deleted_at` | PK `id`。`state ∈ {ready, rejected, deleting, deleted}` |
| `media_refs` | `id`, `asset_id`, `parent_kind`（message/card）, `parent_id`, `channel_id`, `created_at` | `(parent_kind, parent_id)`、`(asset_id)` |
| `media_variants` | `asset_id`, `version`, `variant`（thumb/preview/poster）, `format`, `size`, `state`, `lease_until`, `attempts` | UNIQUE `(asset_id, version, variant)` |
| `media_usage` | `bytes`, `reserved`, `period`, `uploads` | ワークスペースで1行。DO では単一 writer なので競合しない |
| `outbox`（基盤計画の共通テーブル） | `kind = media.delete / media.variant` | DO の alarm で処理する。新しい Queue は作らない |

ルール:
- **org 列を持たない。** DO ではストア自体がワークスペースなので不要。D1 実装だけ全行に `org_id` を足し、すべての問い合わせで条件に入れる。
- **ID からストアを探すグローバル表を作らない。** 外から見えるアドレスにはすべて `orgId` を含める（基盤計画 §3.2）。
- **参照が無くなったら削除する。** 1つの asset を複数の参照（転送したメッセージなど）が指してよい。参照が0になったときだけ `deleting` にし、outbox で R2 から消す。
- **ワークスペースをまたぐ転送は複製する。** 同じ asset を2つのワークスペースで共有しない（削除・保持・データ所在地の規則が混ざるため）。
- **プランの上限値は D1 に置く。** 保存容量や1日のアップロード量の上限は D1 の `entitlements` から読み、DO 側はキャッシュとして持つ。

## 3. アップロード

```
POST /v2/w/:org/media?scope=channel:<id>|card&name=…   （Content-Length 必須、Idempotency-Key 推奨）
→ 201 { asset }        413 上限超過 / 411 長さ不明 / 415 種類不一致 / 429 レート超過 / 507 容量枠超過
```

25 MiB 以下は1回のリクエストで送る。分割転送は上限を上げるときに導入する（段階4）。

1. **認証・認可**
   - セッションとワークスペースのメンバーかを確認する。
   - `scope=channel` はそのチャンネルに投稿できるか（`inChannel`）、`scope=card` はカードを作れるかを確認する。
   - ゲストは自分が入っているチャンネルにだけアップロードできる。
2. **レート制限**（Workers Rate Limiting binding）
   - ユーザーは10分で60件まで。
   - ワークスペースは1時間で2 GB まで（無料プランの初期値。D1 の `entitlements` で上書きできる）。
3. **容量の予約**
   - `Content-Length` を DO の `media_usage.reserved` に条件付きで加算する。上限を超える場合は 507。
   - `Content-Length` が無いリクエストは 411 で拒否する。ブラウザの `fetch(Blob)` も iOS の `URLSession` も付けるので、今のクライアントは影響を受けない。
4. **ストリーミングで保存**
   - `request.body.pipeThrough(new FixedLengthStream(len))` を `MEDIA.put(key, stream)` に渡す。全量はバッファしない。
   - 長さが合わない場合や切断された場合は put が失敗する。R2 は不完全なオブジェクトを残さない。
5. **種類の検証**
   - 最初のチャンクの先頭バイト（マジックナンバー）から実際の形式を判定し、申告と照合する。
   - 表示してよい形式（画像・動画・音声・テキスト）は一致した場合だけ。不一致や不明は `application/octet-stream` として保存し、ダウンロード専用にする。
   - 動画は moov の `stsd` から codec（avc1/hvc1/vp09/av01）を、上限付きの解析で読む。moov が末尾にある場合は末尾を Range で1回だけ読む。
6. **確定**
   - `media_assets` に1行書き、予約を確定する。ここまでを1つのトランザクションで行う。
   - 失敗した場合は予約を戻す。R2 への put が成功したあとに DB の書き込みが失敗した場合は、outbox の `media.delete` で回収する。
   - `Idempotency-Key` が同じ再送には同じ asset を返す。
7. **未使用分の回収**
   - 24時間たっても参照が付かない asset は、DO の alarm で削除する。基盤計画 §4.4 のとおり全テナントを走査する cron は使わない。

端末側の処理（D6・D7）:
- iOS と Android は写真を長辺2560px・JPEG q85 に縮小してから送る。「原寸で送る」を選んだ場合はそのまま送る。
- 動画は H.264/AAC の MP4 に書き出し、faststart（moov を先頭）にする。HEVC のまま送らない。
- 転送はファイルの URL から行い、大きな `Data` や base64 をメモリに持たない。

## 4. 派生物（画像・ポスター）

| variant | 用途 | 仕様 | 作る条件 |
|---|---|---|---|
| `thumb` | 一覧 | 長辺400px、WebP、メタデータ（EXIF・位置情報）を除去 | 原本が長辺600pxより大きいか150 KBより大きい場合だけ。それ以外は原本をそのまま `thumb` として配る |
| `preview` | 拡大表示 | 長辺1600px、WebP、メタデータを除去 | 原本が長辺2000pxより大きいか1.5 MBより大きいか、HEIC の場合 |
| `poster` | 動画一覧 | 端末が作った静止画を、別の画像 asset として検証して紐づける | 無ければ汎用アイコン。サーバーで動画をデコードしない |

- **生成のタイミング:** 最初に要求されたとき（DO の `media_variants` で lease を取り、outbox→alarm で生成）。生成中のレスポンスは `202 pending` で、UI はプレースホルダーを出す。同じ variant を同時に生成しない（UNIQUE と lease）。
- **生成の実装:** `VariantRenderer` というインターフェースを1つ用意し、実装を切り替えられるようにする（§8 の判定条件）。
  - 初期は Images binding（HEIC を含む）。
  - 判定条件を満たしたら、JPEG/PNG/WebP は Worker 内の WASM（例: jSquash）に移す。
- **入力の上限（画像爆弾への対策）:** 5000万画素以下、変換前のサイズは25 MiB 以下とし、Worker の CPU 上限を変換用に設定する。超えた場合は派生物を作らず、ダウンロードだけにする。
- **原本の扱い:** 原本は送られたまま保存する。表示用の派生物だけ位置情報を消す。原本の位置情報については、送信画面と「原寸で送る」の説明に明記する。
- **作り直し:** 変換仕様を上げたときは `version` を上げ、新しいキーに書く。古いキーは outbox で消す。

## 5. 配信と閲覧権限

### 5.1 配信 origin

- **専用ドメイン:** `media.<別の登録ドメイン>`（例: `honmaru-usercontent.net`）。app や api と same-site にならないので、Cookie もサイト内の信頼関係も共有しない。
- **専用 Worker:** 持たせる binding は R2 と署名検証鍵（Secrets）だけ。**D1・DO・セッションは持たせない。** 処理は「トークンを検証する→キーを組み立てる→R2 から get する」だけにして、攻撃面を最小にする。
- **全レスポンスのヘッダー:**
  - `X-Content-Type-Options: nosniff`
  - `Content-Security-Policy: default-src 'none'; sandbox`
  - `Referrer-Policy: no-referrer`
  - `Cross-Origin-Resource-Policy: cross-origin`
  - `Access-Control-Allow-Origin: *`（URL そのものが権限なので、CORS を認可に使わない）
- **表示か保存か:** トークンの `d` で決める。表示を許すのは検証済みの画像・動画・音声・テキストだけで、SVG・HTML・PDF などは常に `attachment` にする。

### 5.2 トークン

```
https://media.…/w/<org>/<asset>/<variant>?v=<version>&e=<exp>&d=<i|a>&k=<kid>&s=<sig>
sig = HMAC-SHA256(key[kid], "m1|org|asset|variant|version|d|e") の先頭128bit
exp = (floor(now / 600) + 2) * 600        // 10分窓。窓の中では同じURL、有効期限は10〜20分
```

- 配信 Worker は署名・期限・パスの形式を検証し、**R2 のキーをトークンの項目だけから組み立てる**。利用者が R2 のキーを指定する余地は無い。
- **鍵:** Workers Secret の `MEDIA_KEYS`（`{kid: key}`）に置き、2つの kid を並べて受け付けることでローテーションする。今 D1 の `kv` にある `file-signing-key` は kid `legacy` として受け付け、次の段階で外す。
- **ログ:** アクセスログ・分析・クラッシュレポートから `s` を除く。

### 5.3 URL の発行（認可）

- **一覧の取得と同時に発行する。** メッセージやカードの一覧を返す API は、すでに閲覧権限を確認している（`inChannel`、`mayReadCard`、個人カードの規則）。そのレスポンスに、添付ごとの署名URLを `variants` として含める。チャットを表示するだけなら、追加の API 呼び出しは不要。
- **期限切れの再発行:** `POST /v2/w/:org/media/urls {refs: [{asset, ref}]}`（1回100件まで）。参照の親（メッセージ・カード）の現在の閲覧権限を確認し、許可されたものだけ返す。asset ID だけでは発行しない。拒否と存在しないものは区別せず、どちらも返さない。
- **未投稿の asset:** アップロードした本人のセッションでだけ発行する。

### 5.4 失効の保証（明記する範囲）

| 事象 | 新しい取得が止まるまで | 補足 |
|---|---|---|
| メッセージの取り消し・ファイルの削除 | R2 から消えた時点（outbox で通常は数秒〜数分） | 消えるまでの間も、新しい URL は発行しない |
| チャンネルからの退出・ワークスペースからの除外 | 最大20分（トークンの寿命） | 基盤計画のアクセストークン（15分）と同水準 |
| 端末に取得済みのデータ | 回収できない | ログアウト・ワークスペースの切り替え・除外の通知でクライアントのキャッシュを消す（§6） |

20分でも許されない契約向けには「厳格モード」を用意する（組織の設定）。窓を1分にし、オブジェクト単位の失効リストを KV に置いて配信 Worker が参照する。初期は実装しない。

### 5.5 キャッシュ

- **サーバー側:** エッジキャッシュは使わない。10万 MAU でも Class B は月$17（§8）なので、Cache API を使った場合のテナント間の取り違えや削除漏れのリスクに見合わない。必要になったら、`org/asset/variant@version` をキーに、トークン検証の後で入れる。
- **レスポンス:** `Cache-Control: private, max-age=<exp までの秒数>`、`ETag: "<version>-<variant>"`。内容は version ごとに不変。
- **クライアント:** URL ではなく `org/asset/variant@version` をキーに、端末の上限付きディスクキャッシュへ入れる（§6）。窓が変わってURLが変わっても再取得しない。サーバーが受けるのは「端末×asset×variant」につき原則1回になる。

### 5.6 Range と動画

- `HEAD, GET, Range, If-Range, ETag` と `200/206/304/416` を、今の `byteRange` と同じ規則で扱う。
- 1回の Range 要求は R2 の Class B 1回と Worker の1リクエストになる。D1 や DO は読まない（今は1回ごとに D1 を読んでいる）。
- 再生中に有効期限が切れた場合は、新しい URL を取り直して再生位置を引き継ぐ。窓は最低10分あるので、通常の1分前後の動画ではまず起きない。長い動画のための更新処理は段階1の実機試験の対象にする。

## 6. クライアント

| | キャッシュ | 消すタイミング |
|---|---|---|
| Web・デスクトップ | Service Worker の CacheStorage `media-<userId>`。キーは `org/asset/variant@version`、上限200 MB の LRU。対象は thumb・preview・poster と5 MB 以下の原本だけ（動画はブラウザのメディアキャッシュに任せる） | ログアウト、アカウントの切り替え、ワークスペースからの除外の通知。**注意:** `sw.js` の activate は SHELL 以外のキャッシュを全部消すので、`media-*` を除外する |
| iOS | URLCache か Kingfisher 等に独自のキャッシュキーを渡す | 同上と、アプリ起動時の一時ファイル清掃 |
| Android（Expo） | expo-image の `cacheKey` | 同上 |

- 一覧は `thumb` を遅延読み込みする。タップするとアプリ内のビューアで `preview` を表示する。原本は「保存」を明示したときだけ取得する。
- 動画は一覧では `poster` だけを表示し、自動再生しない。タップしてから URL を取得して再生する。
- **CSP の更新:**
  - Web の CSP と、デスクトップの `apps/desktop/src/csp.js`（`img-src` と `media-src`）に、配信 origin を足す。
  - デスクトップの `media-src` は今 app と api と blob だけなので、追加しないと動画が再生できない。
- 403 や 404 は再試行しない。401 や期限切れは URL を1回だけ取り直す。

## 7. 脅威と対策

| 脅威 | 対策 | 確認方法 |
|---|---|---|
| 他テナントの取得 | トークンに org を含めて署名する。キーは `org/<org>/…` をトークンから組み立てる。DO はワークスペース単位 | 他 org の asset に自分の org のトークンを組み合わせると 404 になるテスト |
| IDOR（ID の推測） | asset ID は UUIDv7（推測可能な部分を含む）だが、認可は署名で行う。署名なしでは取得できない | 署名なし・改ざん・variant 差し替え・期限切れが 404 になるテスト |
| 退出後の閲覧 | 発行時に参照の親の現在の権限を見る。URL の寿命は最大20分 | 退出の直後に発行が拒否され、20分後に取得が拒否されるテスト |
| アップロード物による XSS | 別の登録ドメイン、sandbox CSP、`nosniff`、検証済みの形式だけ表示、SVG/HTML/PDF は attachment | 偽装 PNG、HTML、SVG、polyglot ファイルの E2E |
| マルウェアの配布 | 危険な形式はダウンロード専用で、警告文を出す。「検査済み」とは表示しない。エンタープライズ向けに検査フック（`quarantined` 状態）を後から追加できる形にする | 段階3以降 |
| 画像・展開爆弾 | 画素数と入力サイズの上限、変換用の CPU 上限。超えたらダウンロードだけにする | 巨大な寸法・壊れたファイル・アニメーションの試験 |
| 容量・費用の乱用 | Content-Length 必須、FixedLengthStream、予約制の容量枠、ユーザーと org のレート制限、未投稿の24時間回収、Analytics Engine での org 別の量の監視 | 50同時×25 MiB、サイズ偽装、切断を混ぜた負荷試験 |
| トークンの漏洩 | 寿命10〜20分。variant と表示/保存の別に縛る。ログから署名を除く。`Referrer-Policy: no-referrer` | ログ出力の検査 |
| 削除漏れ | 削除の失敗を握りつぶさない。outbox で再試行し、上限を超えたらアラートを出す。R2 と DB の照合ジョブ | 削除の失敗を注入する試験 |
| 位置情報の漏洩 | 派生物は位置情報を除く。原本はそのまま保存し、送る前に明示する。写真は既定で縮小して送り、縮小の時点で位置情報を除く | 位置情報付きの JPEG と HEIC の試験 |
| 法的保持との衝突 | 法的保持や保持期間の対象は、削除も回収もしない（`governance.js` の規則を再利用） | 既存の保持テストに媒体を追加 |
| 署名鍵の流出 | Secrets の kid でローテーションする。鍵を替えれば発行済みの URL はすべて失効する（最大20分の影響） | ローテーションの手順書 |

## 8. 規模ごとの原価

単価（2026-09、基盤計画 §5 と同じ）:

| 項目 | 単価 |
|---|---|
| R2 保存 | $0.015/GB-月（10 GB まで無料） |
| R2 Class A | $4.50/100万回（100万回まで無料） |
| R2 Class B | $0.36/100万回（1000万回まで無料） |
| Workers | $0.30/100万リクエスト、CPU $0.02/100万 ms |
| Images | $0.50/1000変換（月5,000まで無料） |
| Stream | 保存 $5/1000分、配信 $1/1000分 |

**Images binding 経由の変換の数え方は、段階3に入る前に公式で確認する。** 以下は、1回の変換を1件として数える保守的な前提。

アクティブユーザー1人・1か月あたりの前提（基盤計画の「R2 媒体 +20 MB/月」に合わせる）:

| 項目 | 前提 |
|---|---|
| アップロード | 写真15枚（縮小後1 MB）、動画1本（4 MB）、その他1件（1 MB）で計20 MB。17件 |
| 派生物 | thumb 15件（各30 KB）、preview 6件（各300 KB）で約2.3 MB。変換21回 |
| 12か月後の保存量 | (20＋2.3) MB × 12 ≒ **270 MB/人** |
| 配信（キャッシュに無かった取得） | thumb 400、preview 60、原本10、動画 15回×Range 6 = 90。計**560回** |
| その他の Worker 要求 | URL の再発行 50、アップロード 17 |
| Class A | put 17＋派生物 21＋削除 ≒ **40回** |

**月額（12か月後）**

| 項目 | 1k MAU | 10k MAU | 100k MAU |
|---|---:|---:|---:|
| R2 保存（270 MB/人） | $3.90 | $40.35 | $404.85 |
| R2 Class A（40/人） | $0 | $0 | $13.50 |
| R2 Class B（560/人） | $0 | $0 | $16.56 |
| Workers 要求（630/人） | $0.19 | $1.89 | $18.90 |
| **変換: Images（21/人）** | $8.00 | $102.50 | **$1,047.50** |
| 変換: WASM の場合（400 ms CPU/回） | $0.17 | $1.68 | $16.80 |
| DO の書き込み（約100行/人） | 共通枠の中 | 共通枠の中 | ≒$0〜10 |
| **合計（Images）** | **≒$12** | **≒$145** | **≒$1,500**（$0.015/人） |
| **合計（WASM に移行後）** | **≒$4** | **≒$44** | **≒$470**（$0.0047/人） |

読み取れること:
1. **短期の最大費目は変換、長期の最大費目は保存。** 10k MAU 前後で Images の変換費が保存費を超える。そのため D5 では「変換費が月$100を超えたら JPEG/PNG/WebP を WASM へ」とした。HEIC だけ Images に残せば、変換費はおよそ1/10以下になる。
2. **キャッシュを効かせれば配信費は小さい。** 10万 MAU でも Class B と Workers の要求で月$35ほど。5分ごとにURLを変えて端末キャッシュが効かない設計にすると、配信回数は数倍〜十数倍になり、ここが数百ドル規模になる。
3. **保存量は縮小送信（D7）と保持期間で抑える。** 写真を縮小しないと（1枚3〜4 MB）、保存量は約2.7倍の720 MB/人になり、10万 MAU で月$1,080前後になる。古い原本を R2 Infrequent Access（$0.01/GB-月、取り出し $0.01/GB、最低30日）に移すと、さらに約20%下がる。ただし閲覧の多い組織では取り出し費で逆転するので、経過日数ごとの閲覧の分布を測ってから決める。
4. **Stream は条件付きで別勘定。** 例として、非互換動画の5%（10万 MAU で月5,000本・各1分）を変換し、各20回再生される場合、保存は月+$25、配信は月+$100。組織ごとの予算枠を超えたら、新しい変換を止める。

**コストの守り（実装する仕組み）**
- プランごとの保存上限と1日のアップロード上限を D1 の `entitlements` に置く。80%で通知し、100%で新規アップロードを止める。閲覧と削除は続けられる。
- org 別の保存量・変換数・配信数・Stream の分数を Analytics Engine に送る。前日比で異常に増えたワークスペースを1時間以内に検知する（基盤計画 §5.3）。
- 容量の上限と金額の予算は別物として扱う。アップロードを止めても既存の閲覧は続くので、配信費は発生し続ける。

## 9. 段階的な移行

## 10. リリースの判定（staging の目標）

- 50同時×25 MiB のアップロードを15分続ける。切断・サイズ偽装・再送を混ぜても、上限を超えた保存、二重の課金、検証前の公開が0件。Worker のメモリがファイルサイズに比例して増えない。
- 500同時閲覧（一覧・preview・動画の Range）を15分続ける。5xx が0.1%未満。配信 Worker の TTFB p95 が200 ms 以下。D1 と DO の読み取りが0回。
- セキュリティ試験:
  - 他 org、退出済み、DM の部外者、ゲスト。
  - 署名の改ざん・期限切れ・variant の差し替え・kid の差し替え。
  - 偽装・polyglot・SVG・HTML・巨大寸法のファイル。
  - 削除と変換の競合、参照の数の境界（転送したメッセージの取り消し）。
- 実機:
  - iPhone の Safari とアプリ、Android の Chrome とアプリ、Mac、Windows の Edge、デスクトップアプリ。
  - JPEG/PNG/HEIC/GIF/WebP、MP4（H.264/HEVC）、MOV、WebM、音声、PDF、壊れたファイル。
  - 低速回線、バックグラウンドからの復帰、10分の窓をまたぐ再生。
- 監視:
  - アップロードの成功率、予約の残留、outbox の最古の未処理、変換の失敗率。
  - org 別の保存量・変換数・配信数。
  - 端末キャッシュのヒット率（クライアントの計測）。
